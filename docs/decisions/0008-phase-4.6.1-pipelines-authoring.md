# 0008: Phase 4.6.1 Create, edit and run Tekton objects (guardrails before auth)

Date: 2026-10-08. Status: accepted.

Tasks, Pipelines and PipelineRuns can be created, edited, started and
deleted in the console before Phase 5. Without per-user rights, the
guardrails below stand in for them. **Phase 5 replaces them with the
user's own RBAC** (impersonation): Capybara will act as the user, and
these guardrails become optional hardening on top.

## Decisions

1. **Project namespaces only.** Plugin objects are written only in Ready
   Project namespaces, never in protected or system namespaces (Projects
   cannot use those). Elsewhere Tekton objects are read-only, including
   Rerun and Cancel.
2. **Permissions.**
   - Capybara's account keeps cluster-wide read on `tekton.dev` (the
     console grant).
   - Create, update and delete on tasks, pipelines and pipelineruns (plus
     patch on pipelineruns for Cancel) come only from a ClusterRole
     `capybara-plugin-tekton-project`, bound by a RoleBinding in each Project
     namespace on that cluster.
   - The plugin controller manages it (manifest `permissions.project`),
     keeps it in step with Projects, and revokes it on uninstall.
   - The installer needs `escalate` and `bind` on that one ClusterRole name,
     plus create/list and name-restricted get/patch/delete on the bindings
     and ServiceAccounts, in both modes.
3. **The `pipeline` ServiceAccount.**
   - Each Project namespace gets one, with no permissions and no API token
     (`automountServiceAccountToken: false`).
   - Runs started from Capybara always use it. Any run or `taskRunSpecs`
     entry naming another ServiceAccount is refused, and so is a rerun of
     such a run (the console offers "Start a new run as pipeline" instead).
   - Starting a run also checks that `pipeline` is Capybara's (labelled)
     and bound to nothing.
   - A same-named account Capybara did not create (OpenShift Pipelines
     makes one per namespace) is never adopted; that namespace is
     reported, and runs there are refused.
   - A per-Project opt-in to a token or permissions could come after
     Phase 5, decided with the user's own rights.
4. **No Secrets.**
   - Tasks, Pipelines and runs may not mount Secrets (volumes, workspaces,
     projected volumes, pod template volumes, image pull Secrets) or read
     them through the environment (`secretKeyRef`, `envFrom.secretRef`).
   - This covers steps, the step template and sidecars, and inline task
     and pipeline specs at any depth.
   - Run workspaces are limited to emptyDir, a volumeClaimTemplate within
     the Project's remaining storage and claim quota, or a ConfigMap in the
     namespace.
5. **No privilege.**
   - No privileged containers, added capabilities, host ports, host paths
     or host network (steps, step template, sidecars, pod templates).
   - StepAction references (step `ref`) are refused for now, rather than
     validating the referenced StepActions.
   - Only Tasks and Pipelines in the same namespace, by name: no resolvers,
     bundles or custom tasks.
6. **Pod Security as a backstop.**
   - The Project controller labels every Project namespace
     `pod-security.kubernetes.io/enforce=baseline`, `warn=restricted`.
   - Labels only affect pods when they are created. Before labelling an
     existing namespace, the controller dry-runs the change and records
     Kubernetes' warnings about running pods that violate the level in
     the Project's status (`podSecurity`, condition `PodSecurity`). They
     keep running, but fail on their next restart.
7. **Core validates, plugins declare.** The rules are data in the plugin's
   manifest:
   - `objects`: kinds, verbs, audit names, references, cleanup;
   - `policies`: a closed set of rules over field paths.
   Core evaluates them on every create, edit and run, then checks quota,
   the Project's ServiceAccounts and referenced objects, and dry-runs the
   write through the cluster's admission. Plugin code never decides what
   is written. Writes are audited fail-closed as `tekton.create`,
   `tekton.update`, `tekton.delete` and `tekton.start`; refusals are
   recorded as denied.
8. **Core's generic writes step aside.** Core's Edit YAML and Delete refuse
   kinds a plugin governs. The YAML tab stays readable, with
   "Edit in Pipelines".
9. **Extension API 1.2.** Plugins get:
   - the console's YAML editor (problems shown as markers on their lines)
     and diff, and its YAML helpers;
   - `pluginObjects` and navigation helpers;
   - a "create" button for registered resources;
   - per-object `appliesTo` for resource actions.
   Tekton 0.2.0 requires 1.2.
10. **The admission dry-run step is gone.** Tekton's "PipelineRuns accepted"
    step dry-ran a run in `default` as Capybara. That now needs write
    access outside Projects, which Capybara no longer has. The webhook's
    workload step covers install mode.

11. **A passing problem does not unload a plugin.** An installed plugin
    stays usable (UI loaded, writes allowed) while a step re-check fails;
    the card shows the error. A workload counts as ready once one replica
    is (an autoscaler adding replicas is not a failure). Before this, the
    webhook scaling up under load flipped Tekton to Error and unloaded open
    pages.

12. **Runs are created and started in one step, from one form.** Create
    PipelineRun (from the list, or Start on a Pipeline) and Create TaskRun
    use the same form and the same server endpoint; Tekton starts the run
    at once (no pending runs: the policies refuse a run created with any
    `spec.status`). TaskRuns are a declared object with their own policy
    (the `pipeline` account on `spec.serviceAccountName`, the same workspace,
    pod template and quota rules). Start last run copies the Pipeline's
    newest run (as Rerun does). Stop (`StoppedRunFinally`: no new tasks;
    running and finally tasks finish) is a declared action next to Cancel.

## Accepted risks until Phase 5

- Every console user can create and run Tasks and Pipelines in any Project
  namespace, as that Project's `pipeline` account. That account has no
  permissions and no token, but steps run arbitrary code with the
  Project's quota and network.
- Project NetworkPolicies limit ingress only: steps can still reach the
  network (and the internet, if the cluster can).
- Objects changed with kubectl are checked only when Capybara writes or
  starts them (a run checks its Pipeline and Tasks as they are then).
