# 0006: Phase 4.5 Plugin framework

Date: 2026-10-07. Status: accepted.

## Decisions

1. **Plugins are catalog entries, installations are per cluster.**
   `PluginRepository` (catalog source, `trusted`), `Plugin` (synced from a
   manifest, `plugins/<name>/plugin.yaml`) and `PluginInstallation`
   (`<plugin>.<cluster>`: mode, config, enabled) live in capybara-mgmt.
   Only `builtin` repositories (the `plugins/` directory) sync in this
   phase; `helm` and `oci` are accepted by the CRD and reported as not
   synced. Untrusted repositories make nothing installable and no bundle
   is served.
2. **Install and enable are separate.** Installing deploys (or connects);
   enabling shows the UI. Disabling hides the plugin's UI on that cluster
   and leaves the tool running. Enable/disable never re-applies the chart
   (the controller applies only when version, mode or config change).
3. **Installer credential, separate and optional.** kube-prometheus-stack
   needs CRDs, ClusterRoles, bindings and webhooks, which the
   least-privilege account cannot create. Each cluster may have an
   installer kubeconfig (Secret type `installer-kubeconfig`), set and
   removed through write-only, audited API calls. Only the plugin
   controller reads it, through its own cache; the API server never loads
   it, so the console proxy cannot use it. The Clusters page shows whether
   plugin installs are Enabled, Disabled or in Error.
4. **Declared installer permissions are per mode.**
   - Install: what the chart creates (checked against a render before
     installing), Helm's release Secrets, and `escalate`/`bind` on roles,
     because the chart's own ClusterRoles grant permissions the installer
     need not hold. This is close to cluster-admin; that is why it is
     separate, optional and controller-only.
   - Connect existing: a Role in the connected service's namespace only:
     create the backend's ServiceAccount, Role and RoleBinding (get, patch
     and delete restricted to `capybara-plugin-<name>`), `create
     serviceaccounts/token` for that account (to mint its short-lived
     tokens; there are no long-lived token Secrets), and `get
     services/proxy` on exactly the connected `service:port`, which RBAC
     requires before the installer may grant it.
   - `hack/capybara-sa.sh <id> --installer <plugin> [--connect --set k=v]`
     creates the account from the manifest (`cmd/plugin-rbac`).
   - Pre-flight checks every declared permission with
     SelfSubjectAccessReviews for the chosen mode and refuses with the
     missing list and the exact command to fix it; it also refuses install
     mode on OpenShift (`refuseInstallOn`) and over CRDs another
     installation owns. Helm installs `crds/` without ownership metadata,
     so the controller labels the chart's CRDs `platform.capybara.io/plugin`
     after installing; a re-install accepts those.
5. **Plugin backends get their own credentials, limited to what the plugin
   declared.**
   - Capybara issues each backend a random credential at startup (file
     mode 600, only its hash in memory; a restart rotates it).
   - Backends call `/internal/plugins/<name>/clusters/<id>/services/<svc>/…`.
     Capybara checks the credential, that the plugin is Ready and enabled
     on that cluster, and the declared service, methods and path prefixes,
     then calls the cluster with the plugin's own short-lived token.
   - That token belongs to `capybara-plugin-<name>` in the plugin's
     namespace, whose Role allows `services/proxy` on exactly the declared
     `service:port` names, with the RBAC verbs of the declared methods
     (POST is `create` through the service proxy). `services/proxy` is
     never part of `capybara-manager`.
   - Monitoring declares Prometheus (GET, query/alerts/rules/targets/
     buildinfo/ready paths) and, in install mode only, Grafana (GET and
     POST, for its UI as an anonymous Viewer).
   - The browser reaches backends only through `/api/plugins/<name>/…`
     (credentials stripped, the user passed as `X-Capybara-User`). Plugin
     code never runs in the Capybara process. In development backends are
     host processes started by `make dev`; they become pods with the Helm
     packaging.
   - The kube-apiserver rewrites absolute links in HTML it proxies;
     Capybara's scoped proxy undoes that, so Grafana works under its
     Capybara sub-path.
6. **UI bundles: trusted, pinned, verified twice.** Bundles are served only
   from trusted repositories and only when the bytes match the sha256
   pinned in the manifest (URL `/api/plugins/_ui/<name>/<sha256>.js`). The
   console fetches the bytes, checks the sha256 again, and imports exactly
   those bytes. `--plugin-dev-dir` (loopback only) serves unpinned dev
   bundles, marked in the UI.
   **Bundles run with full console access: they execute in the console's
   page, with its origin and session. Sandboxing (iframes or workers with
   a message API) is deferred.** Trust in the repository is the control.
7. **Reproducible bundles.** `ui/dist` is committed. Builds pin the Node
   version (`.nvmrc`, `engine-strict`), the lockfile and exact versions;
   `make lint` rebuilds the bundle and fails unless the bytes equal the
   committed file and the pin.
8. **Shared modules.** Plugins import `vue`, `pinia`, `naive-ui` and
   `@capybara/sdk` as bare modules and must not bundle them. Capybara
   serves `/capybara-shared/<name>.js` modules that re-export its own
   copies, and an import map maps the bare names to them:
   - dev: Vite virtual modules; their `export * from 'vue'` is rewritten to
     the same pre-bundled dependency URL the app imports;
   - build: extra entries with fixed names and kept signatures, sharing the
     app's chunks.
   Either way there is one Vue instance. The extension API is versioned
   (`EXTENSION_API_VERSION` in `sdk/`, checked in Go and in the browser);
   bundles for another version are refused, and plugin extension ids must
   start with `<plugin>.`. Each plugin extension is active only on clusters
   where that plugin is installed and enabled.
9. **Secrets never travel in values.** Generated Secrets (the Grafana admin
   password) are created in the cluster before the chart and referenced
   (`grafana.admin.existingSecret`); they are not in Helm values, the
   installation, audit entries or API responses. Connect-mode bearer tokens
   are write-only (own Secret type). Reveal, edit and delete refuse every
   Capybara credential Secret type on every cluster.
10. **Grafana is an anonymous Viewer through Capybara's proxy** for now.
    Phase 5 moves it to Grafana's auth proxy mode with the Capybara user in
    a header.
11. **Audit.** Install, connect, upgrade, configure, enable, disable,
    uninstall, installer and connect-token changes are audited fail-closed.
    The controller's Helm install/upgrade/uninstall and CRD removal are
    audited under the requesting user and linked to the request (`ref`).
12. **Uninstall.** Type-the-name. Install mode asks whether to keep data
    (PersistentVolumeClaims) and warns that CRDs stay. Removing CRDs is
    opt-in: the controller scans for objects of those kinds that are not
    from the release, the user confirms that exact list (by hash), and the
    controller removes the CRDs only if a fresh scan still matches;
    otherwise it keeps them and records a `denied` entry. Cluster removal
    is refused while plugins are installed, unless abandoned (left running,
    unmanaged).
13. **Images** for the small preset are pinned by digest
    (`plugins/monitoring/images.txt`, checked against a render by
    `make lint`). quay.io, registry.k8s.io, docker.io and ghcr.io all pulled
    on the host and from the k3d nodes; images are imported anyway
    (`make plugin-images`), as in ADR 0002.
14. **OpenShift Thanos Querier (connect mode) is implemented and unit-tested
    but UNTESTED on real OpenShift, and unusable until Phase 5.** The
    kube-apiserver drops the client's `Authorization` header after
    authenticating, so a bearer token cannot reach Thanos through the
    service proxy; the connection must use the route (port 9091 with
    `cluster-monitoring-view`, or a tenancy endpoint with the `namespace`
    parameter). Non-loopback hosts are refused until Phase 5's host
    allowlist.
