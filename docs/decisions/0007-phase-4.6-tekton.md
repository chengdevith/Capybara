# 0007: Phase 4.6 Pipelines (Tekton) plugin

Date: 2026-10-07. Status: accepted.

The second plugin, and the first without a backend. It proves that the
framework from Phase 4.5 carries a plugin that is mostly views over a
tool's own resources, and it generalises what Monitoring had hard-coded.

## Decisions

1. **Scope: viewing and safe actions only.** Pipelines, PipelineRuns
   (status, duration), TaskRuns and step logs; Rerun and Cancel of a
   PipelineRun; the latest runs on each Project's page. No Git, registry,
   Tekton Hub or credential management before Phase 5: those need per-user
   rights and secret handling that do not exist yet.
2. **No backend.** The UI reads through the core proxy and watch, and step
   logs reuse core pod log streaming. Plugins therefore get no backend
   account or token unless they declare services.
3. **Console permissions.** A plugin may declare `permissions.console`.
   While it is installed (or connected) on a cluster, the controller
   grants exactly those rules to Capybara's own account there
   (ClusterRole and binding `capybara-plugin-<name>-console`, the subject
   taken from `Cluster.status.identity`), and revokes them on uninstall.
   The installer credential must hold what it grants (RBAC), so creating
   that ClusterRole and binding, plus the console rules, is added to the
   installer's rules for both modes. Tekton's grant: read Pipelines,
   PipelineRuns, Tasks, TaskRuns, CustomRuns and StepActions; `create` and
   `patch` on PipelineRuns.
4. **`create` on PipelineRuns is powerful.** A PipelineRun can name any
   ServiceAccount in its namespace (`taskRunTemplate.serviceAccountName`),
   and Tekton does not check that the creator may use it. So whoever can
   create PipelineRuns in a namespace can run code as any ServiceAccount
   there. Capybara holds this only through the plugin's console grant and
   uses it only for declared actions (below).
5. **Declared actions, run by core.** Writes a plugin's UI may cause are
   declared in its manifest (`actions`): `copy` (a new object from
   declared `spec.*` fields, `generateName` from the original, the
   original's labels except the tool's own, annotation
   `platform.capybara.io/copy-of`) or `patch` (a fixed merge patch), with
   an optional `when` condition. Core runs them at
   `POST /api/clusters/{id}/plugin-actions/{plugin}/{action}` only while the
   plugin is Ready and enabled there, checks the object's uid, and audits
   each run (fail-closed) as `<plugin>.<action>`. Nothing written comes
   from plugin code or the request body. The manifest is refused unless
   the console grant allows the action's verb.
   - Rerun = copy of `pipelineRef`, `pipelineSpec` (only present when the
     original had an inline spec), `params`, `workspaces`,
     `taskRunTemplate`, `timeouts`; never `status` or the cancel state.
   - Cancel = patch `{"spec":{"status":"Cancelled"}}` while `Succeeded` is
     `Unknown`; refused (409) once the run has finished.
6. **Before authentication, every user may rerun and cancel.** Acceptable
   until Phase 5 (all users are "dev" today). From Phase 5, plugin actions
   must be checked against the requesting user's own rights (impersonated
   SubjectAccessReview for the action's verb and resource in the object's
   namespace) before core runs them.
7. **Packaging: the upstream release, vendored and pinned.** Tekton ships
   `release.yaml`, not a chart. `plugins/tekton/upstream/release-v1.17.0.yaml`
   is vendored (sha256 `93ee4eda…44ff349`) and `cmd/plugin-chart` builds a
   deterministic chart from it (`upstream/build.yaml`): the 8 CRDs go to
   `crds/`, everything else to `templates/` unchanged; a manifest with
   `{{` is refused. The only edits are declared there: the
   `tekton-pipelines` Namespace is dropped (Helm's release namespace; the
   controller creates it with upstream's labels, including Pod Security
   `restricted`, through the new `chart.namespaceLabels`), and resolver
   flags are set. `make lint` rebuilds the archive and fails unless it is
   byte for byte the committed, pinned one. Release `capybara-tekton` in
   `tekton-pipelines`.
8. **Only the cluster resolver.** The git, hub, bundles and http resolvers
   fetch remote code and need credential handling that waits for Phase 5;
   they are disabled. Pipelines and Tasks come from the cluster.
9. **Connect existing, and never a second Tekton.** A `detect` block names
   what an existing install serves: Connect needs `tekton.dev/pipelineruns`
   (or OpenShift Pipelines' `operator.tekton.dev/tektonconfigs`); Install
   is refused when those CRDs belong to another installation, when the
   `openshift-pipelines` namespace exists, or on OpenShift
   (`refuseInstallOn`). Connect only creates the console grant.
10. **Images pinned by digest.** Upstream references its images by digest
    (`repo:tag@sha256:<index>`), and its controller names more images in
    `-…-image` flags. `cmd/plugin-images` reads both;
    `plugins/<p>/images.txt` lists every image the chart names, with
    `skip` for ones never run here (Tekton's Windows shell image,
    Monitoring's Thanos). `make plugin-images` imports the node's platform
    and then names it by the index digest on each node
    (`ctr images tag`), so the kubelet finds it and never pulls.
11. **CRD upgrades.** Helm never upgrades `crds/`, so before every Helm
    install or upgrade the controller server-side applies the chart's CRDs
    itself (field manager `capybara-controller`, labelled with the plugin),
    after a pre-flight check that the installer credential may create and
    patch them. This applies to every plugin, Monitoring included.
12. **Extension API minor versions.** The console exposes 1.N
    (`EXTENSION_API_MINOR`, now 1.1); a plugin declares the minimum it
    needs (`minExtensionApi` in plugin.yaml, `minApi` in the bundle), and
    an older console refuses it with "needs extension API 1.M; this
    Capybara provides 1.N". 1.1 adds `registerResource` (the console's
    generic list and detail pages for a plugin's kinds, gated per cluster
    like every plugin extension), `components.LogViewer` and
    `components.ResourceLink`, `composables.useLiveList`, and
    `pluginAction()`. Monitoring declares 1.0, Tekton 1.1.
13. **Tooling loops over plugins.** The Makefile, lint and `make dev` find
    plugins by what they contain (`ui/`, `backend/` with `dev.addr`,
    `images.txt`, `upstream/build.yaml`); plugin UIs share
    `plugins/_ui-build` (Vite config, Node-version and bundle checks).

14. **Found by the e2e run, fixed in the framework.**
    - The pre-flight refuses a chart object the installer may create but
      not delete (Tekton's resolvers Namespace stopped its uninstall
      halfway).
    - The installer must be able to list every kind its chart's CRDs
      define: uninstall's CRD scan reads them (a test checks every plugin).
    - A plugin has data only if its installer may list and delete
      PersistentVolumeClaims (`HasData`); only then does uninstall offer to
      keep data, and otherwise it skips that step.
    - The installation controller reads each installation from the API
      server, not the cache. An apply writes status before and after a
      long Helm run; the first write queued the next reconcile, which read
      a cache without the final write and applied again, every ~30 s, for
      every plugin (since Phase 4.5). Each re-apply flipped the
      installation out of Ready and made the console unload the plugin's
      UI.

15. **Fixed after the phase-4.6 tag: refusals stay visible.** The
    installation controller reacted to its own status writes, so a refused
    install (e.g. an installer credential made for another plugin) re-ran
    its pre-flight in a loop and showed Installing, its Error with the fix
    command replaced within milliseconds. It now reacts to spec,
    annotation, label and deletion changes only (plus explicit requeues and
    installer-credential events), and the pre-flight's access reviews are
    no longer throttled to 5 requests/s (a refusal took ~30 s).

## Consequences

- A plugin like Tekton is a manifest, a generated chart and a small UI
  bundle; no Go code of its own.
- The console grant widens Capybara's own account on clusters where such a
  plugin is installed. It is visible (one named ClusterRole), removed on
  uninstall, and exercised only through declared, audited actions.
- Rebuilding a plugin bundle changes its pin; a running controller serves
  the new one after its next catalog sync (5 minutes, or on any change to
  the PluginRepository).
