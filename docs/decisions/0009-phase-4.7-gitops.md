# 0009: Phase 4.7 GitOps with Argo CD (Applications per Project, before auth)

Date: 2026-10-08. Status: accepted.

The GitOps plugin (id `argocd`) installs Argo CD on a cluster, or connects
to one already there, and lets each Project manage Argo CD Applications in
its own namespace. Like ADR 0008, it comes before Phase 5: there are no
per-user rights yet, so the guardrails below stand in for them. **Phase 5
replaces them with the user's own RBAC** (impersonation).

## Decisions

1. **A small Argo CD.**
   - The vendored argo-cd chart 10.10.1 (Argo CD v3.5.4), pinned by sha256.
   - The preset runs only the application controller, the repo server and
     Redis. Capybara's console is the UI, so there is no Argo CD API server,
     Dex or notifications, and no Argo CD users.
   - The ApplicationSet controller has 0 replicas. Capybara grants no
     permission on ApplicationSets anywhere: they could create Applications
     outside these rules.
   - Images are pinned by digest and imported into k3d (nodes never pull).
   - Redis's password is a Secret Capybara generates before installing,
     never in values, the installation or audit entries.
   - A proxy for Git servers can be set at install (`httpProxy`,
     `httpsProxy`, `noProxy`), passed to the repo server.
   - The `argocd` namespace enforces Pod Security `restricted`; every
     component starts under it (tested end to end).
2. **Applications in any namespace, scoped by AppProjects.**
   - Argo CD accepts Applications outside its own namespace
     (`application.namespaces: "*"`). Which Applications may do what is
     decided per AppProject.
   - Each Ready Project gets a generated AppProject `capybara-<project>` in
     Argo CD's namespace. It accepts Applications only from the Project's
     namespace and deploys only into that namespace on this cluster.
     Cluster-scoped kinds are not allowed. ResourceQuota, LimitRange,
     NetworkPolicy and RoleBinding are refused, so an Application cannot
     undo what the Project controller set.
   - The `default` AppProject is locked: no sources, destinations or kinds,
     and no other namespaces. It is a post-install/upgrade chart hook
     (re-created on each upgrade), because the CRD only exists once the
     chart is applied.
   - Generated objects are a framework feature (`permissions.project.objects`):
     applied with the installer credential, labelled, never adopting an
     existing object, removed with the Project and on uninstall.
3. **The Application policy.** Core checks every create and edit:
   - `spec.project` is the Project's `capybara-<project>`; the destination
     is the Project's namespace on `https://kubernetes.default.svc`;
     destination by name is refused.
   - Repository URLs: `https://` anywhere; `http://` and `git://` only to
     services in the cluster (`*.svc`, `*.svc.cluster.local`); no SSH.
     There are no repository credentials before Phase 5.
   - One source (`spec.sources` refused); no config management plugins;
     no source hydration.
   - The namespace is never created or relabelled by the Application
     (`CreateNamespace=true` and `managedNamespaceMetadata` refused): it is
     the Project's, with its Pod Security labels.
   - Only Argo CD's resources finalizers; no `operation` written directly.
4. **Actions.** Declared in the manifest, run by core, audited as
   `argocd.<action>`, only in Project namespaces:
   - Sync (an optional revision; prune asks for the Application's name),
     Refresh, Hard refresh.
   - Sync policy: auto-sync on/off, self-heal on/off, auto-prune on/off
     (turning auto-prune on asks for the name).
   - **Sync to this revision** (from History) is a one-off manual sync.
     It is offered only without auto-sync (which would sync back) and for a
     single source, and never prunes.
   - Delete chooses what happens to what the Application deployed: removed
     with it (Argo CD's cascade finalizer) or left running.
5. **Some charts are refused at sync.** Argo CD checks each resource
   against the AppProject when it syncs, not when the Application is
   written. A chart that needs a RoleBinding, a cluster-scoped resource or a
   quota change fails to sync. The console explains each such refusal in
   Project terms on the Resources tab. Roles and ServiceAccounts are
   allowed; RoleBindings wait for per-user rights in Phase 5.
6. **Uninstall safety.**
   - The chart renders its CRDs from templates. A plain uninstall would
     delete them, and with them every Application; cascade finalizers would
     then delete what they deployed, or hang. The preset sets the chart's
     keep option (`helm.sh/resource-policy: keep`), and Capybara's
     pre-flight now refuses any chart whose templated CRDs lack it.
   - Uninstall is refused while any Application exists on the cluster.
     The refusal lists them (marking those that would delete what they
     deployed) and says to delete them first, with one of the two delete
     choices. The API checks before accepting the uninstall; the controller
     checks again before removing anything.
   - Removing the CRDs stays a separate, confirmed choice, possible only
     once no Applications remain.
   - Uninstalling leaves what Applications deployed untouched (tested).
7. **Connect existing, and view-only.**
   - Connect needs Applications to be served. It is refused for install mode
     on OpenShift, which ships OpenShift GitOps (connect to it instead).
   - Writes need Argo CD to accept Applications in Project namespaces: the
     `apps-in-any-namespace` step checks `argocd-cmd-params-cm`
     (`application.namespaces`) or the ArgoCD resource's
     `spec.sourceNamespaces`. When it does not, GitOps is **view-only**:
     Applications can be read, but nothing is created, edited, deleted,
     synced or refreshed.
   - This is the likely first mode on real OpenShift GitOps, whose default
     instance watches only its own namespace. Phase 5 enables writes there,
     with the user's own rights.
   - The step is informational: it never keeps the installation from Ready
     (its state is "Off", shown as not available).
8. **Extension API 1.3.**
   - Action inputs (typed, filled into the declared patch) and name
     confirmation.
   - Delete modes on `pluginObjects.remove`.
   - Server side: per-Project objects, policy placeholders (`{{project}}`,
     `{{namespace}}`, `{{cluster}}`) and a `match` rule, field steps,
     `requiresStep`, uninstall blockers.
   - GitOps 0.1.0 requires 1.3.

## Accepted risks until Phase 5

- Every console user can create Applications in any Project namespace,
  from any https:// repository, and sync them there.
- Argo CD's application controller holds cluster-wide rights (as upstream
  ships it). The AppProjects are what limit each Project's Applications.
- An Application changed with kubectl is checked only when Capybara writes
  it. Argo CD's own AppProject checks still apply when it syncs.
